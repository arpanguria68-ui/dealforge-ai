Architecture

DealForge is a conventional web app wrapped around an unconventional core: a crew of tool-using agents whose work is planned, gated, verified and edited before a human sees it.

The chat pipeline (the path the UI uses)

1
Clarify POST /api/v1/chat/clarify

The ProjectManager agent identifies data needs and asks up to three rounds of questions. The user can skip or answer; skipped questions are self-researched and summarised as assumptions. A prompt that says "do not ask clarifying questions" skips the step. A guard validates prompt length and content first.

2
Plan POST /api/v1/chat/plan

The LLM drafts tasks; the planner then enforces structure: stage dependencies (data → analysis → synthesis), a valuation agent whenever a DCF/LBO is planned, an LBO task routed to the DCF/LBO architect when requested, and focus-mode limits. Tasks persist as a todo list with dependencies.

3
Approve (UI)

The plan is presented with an Approve & run bar. The list can also be edited via /api/v1/tasks/….

4
Execute POST /api/v1/chat/execute-task

One call per task. The server checks that the list is approved and dependencies are done, loads upstream results as context, routes the agent to a provider, and runs it with its tool allow-list under a wall-clock timeout (default 180 s). Results, tool-use outcomes and activity events are stored.

5
Synthesize

The investment-memo agent runs last with every upstream result. Memo grounding and cross-agent reconciliation run here; the chat builds the brief and follow-ups.

6
Deliver

Dashboard metrics and /api/v1/deals/{id}/documents/… read the same persisted results to generate and release reports.

Agent runtime

All agents extend BaseAgent (backend/app/agents/base.py):

  • Tool loop. generate_with_tools lets the model call tools until it produces an answer. Providers with native function calling use it; others (including the OpenAI-compatible custom endpoint) use a text tool protocol where the model emits a JSON block with command and args. The protocol rejects fabricated sources: an agent may not cite a tool it did not call.
  • Allow-lists. AGENT_TOOL_MAP gives each agent only the tools it needs (for example valuation_agent has 15, treasury_agent has 2). Tool-family shortlisting (Laya) narrows the list per task, and retrieval tools are always kept for data-collection tasks.
  • Recorded outcomes. Every call is stored with name, success flag and error, and shown in the dashboard ("4 tool calls ok, 2 failed").
  • Unusable replies. Empty replies, canned chat-product errors ("Sorry, something went wrong…") and short off-topic chatter are treated as failures and retried once, not saved as analysis.
  • Structured output. run_with_structure parses JSON and falls back to narrative with a flag when the model returns prose.

Agent harness

"Harness" here means the code that wraps a model so it behaves like a dependable worker. DealForge has two: a runtime harness around every agent, and a test harness that checks the contracts.

Runtime harness

BaseAgent.run wraps all 29 agents in the same pipeline:

1
Skill injection

Domain skill and sector context are added to the task.

2
Issue tree

A MECE issue tree is generated and validated; context is retrieved per branch.

3
Core run

The agent runs its own logic, including the bounded tool loop.

4
Output validation

Deterministic checks on the output (arithmetic, required fields).

5
Memory

Learnings are stored for later runs.

6
Reflection

A reflection and reward engine scores the output and updates best practices; the score is attached to the result.

7
Messaging

An insight message is emitted on the agent bus.

  • Bounded tool loop: a capped number of tool rounds; calls within a round run concurrently and are returned in order; repeated identical calls are de-duplicated; tool context is size-bounded.
  • Failure isolation: tool timeouts, bad arguments and synchronous tools are contained by the router; a failing LLM provider returns a failed output instead of crashing the run; an agent has a wall-clock deadline (default 180 s).
  • Honest outputs: heuristic tools are labelled as such to the model and in results; a compliance agent without documents reports "unassessed", not "non-compliant".

Test harness

  • tests/test_agentic_harness.py checks that every registered tool has a callable contract (schema, required arguments, description), that every agent allow-list and Laya tool family names only real tools, concurrency and de-duplication in the loop, the Laya cache, coalescing and circuit breaker, provider-failure handling and isolation between concurrent runs on a shared agent.
  • tests/evals/ holds offline behavioral checks with a mocked model: agent contracts, MCP configuration, replication, reports, scenarios, the Scrum Master and tools.

Gap: these are deterministic contract tests. There is no benchmark that scores real-model output across a fixed set of deals; the evaluate_*.py scripts in backend/ are ad hoc.

Laya: the fast classifier layer

Laya is a small "System-1" decision engine. Instead of asking a large model every routing question, DealForge asks Laya typed questions (a choice, a score, a yes/no) and uses the answer to route work. Everything is fail-soft: if Laya is off, missing or slow, callers fall back to the previous keyword or LLM path, and a circuit breaker stops a dead backend from slowing every step.

DecisionWhere it is used
Complexity tier (fast / general / reasoning)ModelRouter picks a provider pool per task; simple tasks go to a local or fast model, hard ones to a reasoning model. Pools are configurable (LAYA_FAST_POOL, LAYA_GENERAL_POOL, LAYA_REASONING_POOL)
Tool family shortlistToolRouter narrows the agent allow-list to the relevant tool family for the task
Deal triage and guardrailLangGraph nodes classify the brief; secrets in briefs (API keys, bearer tokens, private keys) are redacted before any model sees them. Redaction runs even when Laya is unavailable
Confidence gateScores agent output so low-confidence results can trigger review or a retry in the orchestrator
Retrieval relevance and re-rankingHybrid search can re-rank chunks by relevance
Debate agreementDetects whether debating agents have converged

Backends, in priority order: a local in-process router (pip install laya), a remote laya-serve over HTTP, an LM Studio model answering the same typed questions as constrained JSON, then a deterministic keyword heuristic. A decision cache and in-flight de-duplication keep it cheap because the planner, project manager, router and gates often ask the same question. Configure it with LAYA_ENABLED, LAYA_MODE (auto|local|remote|lmstudio|off), LAYA_BASE_URL and the other LAYA_* variables; status is at GET /api/v1/laya/status.

Confidences are calibrated only with the local or remote checkpoints; the LM Studio backend reports uncalibrated model confidence. The demo runs on this site do not claim which backend was active.

Orchestration modes

The same agents can be driven three ways:

ModeEntry pointStatus
Interactive chat pipeline (plan → approve → execute-task)/api/v1/chat/*, /api/v1/tasks/*Primary path. Exercised end to end and covered by tests
Deal orchestrator (LangGraph state graph)POST /api/v1/deals/{id}/runImplemented, less exercised
OFAS missions (RACI task graph with review gates and recovery)/api/v1/ofas/*Implemented, less exercised
Specialist workflows (GP-led continuation vehicle, LMT stress, Monte Carlo)/api/v1/workflows/*Implemented, less exercised

The deal orchestrator is a LangGraph graph with nodes init → fact_base_ingestion → retrieval → task_generation → screening → parallel_analysis → consistency_check → advanced_financial → data_curator → complex_reasoning → report_architect → debate → red_team → scoring → halugate_verify → stakeholder_simulation → report_formatting → compiler → decision with conditional edges, quality gates, a multi-round agent debate engine, peer confidence gates, an inter-agent message bus, a user-input pause gate and a HaluGate NLI hallucination check. These pieces are in the repository and API-exposed; the product documentation and the demos here concentrate on the interactive pipeline because that is the one verified end to end.

Deployment

Docker Compose defines backend (FastAPI, port 8005→8000), frontend (nginx, port 3000) and redis (7-alpine) with volumes for data and reports. CORS origins, admin-token enforcement, request-size guards (API_MAX_JSON_MB) and path-traversal guards for uploads are configured in the backend.
