Architecture

DealForge is a conventional web app wrapped around an unconventional core: a crew of tool-using agents whose work is planned, gated, verified and edited before a human sees it.

The chat pipeline (the path the UI uses)

1
Clarify POST /api/v1/chat/clarify

The ProjectManager agent identifies data needs and asks up to three rounds of questions. The user can skip or answer; skipped questions are self-researched and summarised as assumptions. A prompt that says "do not ask clarifying questions" skips the step. A guard validates prompt length and content first.

2
Plan POST /api/v1/chat/plan

The LLM drafts tasks; the planner then enforces structure: stage dependencies (data → analysis → synthesis), a valuation agent whenever a DCF/LBO is planned, an LBO task routed to the DCF/LBO architect when requested, and focus-mode limits. Tasks persist as a todo list with dependencies.

3
Approve (UI)

The plan is presented with an Approve & run bar. The list can also be edited via /api/v1/tasks/….

4
Execute POST /api/v1/chat/execute-task

One call per task. The server checks that the list is approved and dependencies are done, loads upstream results as context, routes the agent to a provider, and runs it with its tool allow-list under a wall-clock timeout (default 180 s). Results, tool-use outcomes and activity events are stored.

5
Synthesize

The investment-memo agent runs last with every upstream result. Memo grounding and cross-agent reconciliation run here; the chat builds the brief and follow-ups.

6
Deliver

Dashboard metrics and /api/v1/deals/{id}/documents/… read the same persisted results to generate and release reports.

Agent runtime

All agents extend BaseAgent (backend/app/agents/base.py):

  • Tool loop. generate_with_tools lets the model call tools until it produces an answer. Providers with native function calling use it; others (including the OpenAI-compatible custom endpoint) use a text tool protocol where the model emits a JSON block with command and args. The protocol rejects fabricated sources: an agent may not cite a tool it did not call.
  • Allow-lists. AGENT_TOOL_MAP gives each agent only the tools it needs (for example valuation_agent has 15, treasury_agent has 2). Tool-family shortlisting (Laya) narrows the list per task, and retrieval tools are always kept for data-collection tasks.
  • Recorded outcomes. Every call is stored with name, success flag and error, and shown in the dashboard ("4 tool calls ok, 2 failed").
  • Unusable replies. Empty replies, canned chat-product errors ("Sorry, something went wrong…") and short off-topic chatter are treated as failures and retried once, not saved as analysis.
  • Structured output. run_with_structure parses JSON and falls back to narrative with a flag when the model returns prose.

Model layer

ComponentRole
ModelRouterLocal-first routing: try a local model (Ollama / LM Studio) where configured, escalate to cloud on failure; a per-agent provider map comes from settings. The provider actually used is logged and shown in the UI.
LLM GatewayCentral rolling-window rate limits per vendor, exponential backoff with jitter, cloud→cloud→local fallback, daily budget guards and deterministic-call caching.
Provider clientsGemini, Vertex, Claude, OpenAI, Mistral, Groq, OpenRouter, NVIDIA, local (Ollama / LM Studio) and a generic OpenAI-compatible custom endpoint.
Capability probeDetects what a model/provider supports (for example native tool calls) so the right protocol is used.
Context guard & token budgetKeeps prompts within the model window and tracks usage (GET /api/v1/llm/usage).

Orchestration modes

The same agents can be driven three ways:

ModeEntry pointStatus
Interactive chat pipeline (plan → approve → execute-task)/api/v1/chat/*, /api/v1/tasks/*Primary path. Exercised end to end and covered by tests
Deal orchestrator (LangGraph state graph)POST /api/v1/deals/{id}/runImplemented, less exercised
OFAS missions (RACI task graph with review gates and recovery)/api/v1/ofas/*Implemented, less exercised
Specialist workflows (GP-led continuation vehicle, LMT stress, Monte Carlo)/api/v1/workflows/*Implemented, less exercised

The deal orchestrator is a LangGraph graph with nodes init → fact_base_ingestion → retrieval → task_generation → screening → parallel_analysis → consistency_check → advanced_financial → data_curator → complex_reasoning → report_architect → debate → red_team → scoring → halugate_verify → stakeholder_simulation → report_formatting → compiler → decision with conditional edges, quality gates, a multi-round agent debate engine, peer confidence gates, an inter-agent message bus, a user-input pause gate and a HaluGate NLI hallucination check. These pieces are in the repository and API-exposed; the product documentation and the demos here concentrate on the interactive pipeline because that is the one verified end to end.

Deployment

Docker Compose defines backend (FastAPI, port 8005→8000), frontend (nginx, port 3000) and redis (7-alpine) with volumes for data and reports. CORS origins, admin-token enforcement, request-size guards (API_MAX_JSON_MB) and path-traversal guards for uploads are configured in the backend.
