Knowledge & RAG (PageIndex)

Agents do not read whole files. Uploaded deal documents are turned into a section tree with PageIndex (vectorless, structure-based RAG), and a hybrid search combines three signals to pull the few passages an agent needs. No vector database is required.

Pipeline

1
Ingest

Documents arrive by upload (/documents/upload, bulk, URL, directory) or batch knowledge-base ingestion. PDF, Word, Markdown and plain text are indexed; the knowledge-base ingester also reads Excel and PowerPoint. Each document is tagged with its deal_id. Search queries are passed through the secret redaction used for briefs.

2
Build the tree

For PDFs and Markdown the PageIndex library builds a hierarchical table-of-contents tree with node summaries (an LLM does the summarising, so it needs a key). When the library is not installed or fails, a built-in structure-aware chunker takes over: paragraphs, then sentences, about 1500 characters per chunk with 200 characters of overlap, headings kept as node titles and section paths kept for citations.

3
Store locally

Trees are JSON files in a local storage directory with a catalog. PAGEINDEX_MODE=local (default) is self-hosted; cloud uses the VectifyAI API.

4
Search

A query is scored three ways and the rankings are fused (below). Results come back with excerpts, scores and metadata (document, section path, page).

5
Rerank (optional)

The Laya classifier can re-rank the fused top results in one batched pass. If Laya is off or fails, the fused order is kept.

Hybrid search

SignalWhat it is
TreeKeyword and entity scoring over the PageIndex tree nodes (titles, summaries, text)
BM25Lexical ranking over the chunks
DenseCosine similarity of embeddings: sentence-transformers (all-MiniLM-L6-v2) when installed, otherwise hashed TF-IDF vectors from the standard library
FusionThree-way Reciprocal Rank Fusion. Weights are tunable with RAG_W_TREE, RAG_W_BM25, RAG_W_DENSE or in Settings
RerankRAG_LAYA_RERANK (default on) re-scores the top RAG_RERANK_N (default 30); RAG_DENSE=false switches dense off

How agents use it

  • The document_search tool and each agent's context retrieval query the index. Retrieval is scoped to the active deal; cross-deal memory is opt-in (for example for due diligence), so one deal's documents do not leak into another's analysis. A test enforces this.
  • The orchestrator's retrieval node and the IC memo grounding use the retrieved passages as evidence.
  • Clarification memory stores earlier questions and answers so the Scrum Master can ask better ones.

Deal knowledge graph

Separately from document RAG, agents write facts, entities and risks to a per-deal knowledge graph (SQLite by default, Neo4j optional via KG_BACKEND). Graph Q&A reads the deal's current facts through a parameterised, read-only API and has the model answer only from those facts. It no longer lets the model write Cypher. The graph feeds the cross-agent risk register.

The Knowledge tab in the UI is the front end for the index: upload, list, delete and search.

Limits: the tree summaries need an LLM key when the PageIndex library is used. Tree scoring at query time is keyword-based, not an LLM walk of the tree. Dense retrieval falls back to hashed TF-IDF when sentence-transformers is not installed. Retrieval quality has not been benchmarked on a labelled question set.
